# AI Skincare Planner – Personalized Skin Intelligence

A full-stack, role-based skincare analysis platform. Users upload a facial
photo and get a simulated AI skin assessment (health score, concerns, risk
factors, product recommendations), then can book appointments with doctors
or consultants who review and annotate their reports. Admins manage the
whole platform.

**Stack:** React (Vite) + React Router + Axios · Node.js/Express ·
PostgreSQL · JWT + Google OAuth2 · bcrypt · multer

> This project was built to satisfy two internal module guides:
> **Module 1** (Auth/JWT/OAuth/RBAC — hence the single `users` table with
> a `role` column) and **Module 3** (Skin Assessment Engine — hence the
> `skin_health_score` / concerns / risk-factors shape of each report,
> adapted here into the Node/Express stack instead of FastAPI).

## 3. Backend setup

```bash
cd backend
npm install
cp .env.example .env
```

Edit `.env`:
- Set `PGUSER` / `PGPASSWORD` / `PGDATABASE` to match a Postgres database
  you've created (e.g. `createdb ai_skin_intelligence`).
- Set `JWT_SECRET` and `SESSION_SECRET` to any long random strings.
- Leave `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` blank if you don't need
  Google login yet — the app runs fine without it, the "Continue with
  Google" button just won't complete.

Create the schema and demo accounts:

```bash
npm run db:init
```

This creates all tables and prints four ready-to-use demo logins (see
below). Then start the API:

```bash
npm run dev      # nodemon, auto-restarts on changes
# or
npm start
```

The API runs at `http://localhost:5000`. Check `http://localhost:5000/api/health`.

## 5. ML inference service (optional but recommended)

The skin analysis feature has a real, runnable ML pipeline in `ml/` — a
scikit-learn image classifier (color + texture features → skin type,
plus a rule-based concern layer) trained on a generated sample dataset,
served over HTTP by a small Flask app. Full details, dataset structure,
and the production CNN track are documented in `ml/README.md`.

```bash
cd ml
python3 -m venv venv && source venv/bin/activate
pip install -r requirements-demo.txt
python training/train_demo.py      # trains + saves ml/models/demo_model.joblib
python inference/serve.py          # serves on http://localhost:5001
```

Then set `ML_SERVICE_URL=http://localhost:5001` in `backend/.env` (already
the default in `.env.example`) and restart the backend. Report uploads
will now call the real model; if the service isn't running or errors, the
backend automatically falls back to the simulated analysis (`aiAnalysis.js`)
instead of failing the request — check the `source` field on a saved
report (`ml-service` vs `simulated-fallback`) to see which path was used.

## 6. Google OAuth setup (optional)

1. In [Google Cloud Console](https://console.cloud.google.com/), create an
   OAuth 2.0 Client ID (Web application).
2. Authorized redirect URI: `http://localhost:5000/api/auth/google/callback`
3. Authorized JavaScript origin: `http://localhost:5173`
4. Copy the Client ID/Secret into `backend/.env`.
5. Restart the backend. The "Continue with Google" button on Login/Register
   will now complete the full flow: Google → backend issues a JWT → redirects
   to `frontend/oauth/callback?token=...` → frontend stores the token and
   routes to the right dashboard. New Google sign-ups default to the `USER`
   role (upgrade them from the Admin → Doctors/Consultants tab if needed).

## 7. How authentication & RBAC work

- **Register/Login** (`POST /api/auth/register`, `/login`) hash passwords
  with bcrypt and return a JWT containing `{ id, email, role }`.
- The frontend stores the JWT in `localStorage` and attaches it as
  `Authorization: Bearer <token>` on every API call (`src/api/axios.js`).
- Every protected backend route runs `protect` (verifies the JWT, loads the
  current user) and, where needed, `authorize('ROLE', ...)` to enforce RBAC
  — e.g. only `DOCTOR` can hit `/api/doctor/*`.
- On the frontend, `<ProtectedRoute allowedRoles={[...]}>` blocks
  unauthenticated users (→ `/login`) and redirects wrong-role users to
  their own dashboard rather than showing a 403 page.
- Google OAuth (Passport, stateless) creates or links an account, then
  issues the same kind of JWT — so once logged in, Google and
  email/password users are indistinguishable to the rest of the app.

## 8. AI skin analysis

Uploading a photo (`POST /api/reports/upload`) calls
`backend/src/utils/mlClient.js`, which sends the image to the Python ML
service (§5) and returns skin type, a 0–100 health score, prioritized
concerns, and matching product recommendations — stored in `skin_reports`
and viewable in "My Reports". If the ML service isn't configured or is
unreachable, the same request transparently falls back to
`aiAnalysis.js`'s simulated analysis so uploads never fail outright.
Either way, results are always presented as an AI-assisted informational
estimate, never a medical diagnosis — the UI and API both carry that
disclaimer. Doctors can add diagnosis notes; consultants can
override/add recommendations — both mark the report `REVIEWED`.

## 9. Skincare plan / routine generation

From the "Skincare Plan" tab (or the "Build My Skincare Plan" prompt
after an analysis), `POST /api/skincare-plan/generate` builds a full plan
from the user's latest report — see `backend/src/utils/routineGenerator.js`:

- **Morning routine** — Cleanser → Treatment → Moisturizer → Sunscreen
- **Evening routine** — Cleanser → Treatment → Moisturizer → Night Care
- **Weekly treatment plan** — 2–4 targeted treatments (masks, exfoliation)
  with a frequency, chosen from the user's detected concerns
- **Seasonal recommendations** — 3 tips based on the current calendar
  season (Spring/Summer/Autumn/Winter)

Each step names a product category and a plain-language reason it's
included, driven by rules keyed to the report's concerns (e.g. an "Acne"
concern swaps in a salicylic acid treatment step and a clay mask). Plans
are persisted to `skincare_plans` so `GET /api/skincare-plan` always
returns the latest one, and `GET /api/skincare-plan/history` returns all
of them.

## 9a. Ingredient intelligence & product recommendations

Two dedicated systems, backed by their own PostgreSQL tables, sit
alongside the routine generator above (they don't replace it — the
routine's own step-by-step logic in `routineGenerator.js` is unchanged):

- **`ingredients` table** (17 seeded rows) — name, category, benefits,
  suitable skin types/concerns, irritation potential, allergy notes,
  comedogenic rating, usage guidance. Queried by
  `backend/src/services/ingredientIntelligence.js`, which both (a) powers
  `GET /api/ingredients` (search/filter) and `GET /api/ingredients/for-me`
  (personalized suitable/caution/avoid breakdown), and (b) supplies the
  shared allergy-matching primitives (`normalizeTerms`/`textConflicts`)
  that `routineGenerator.js` now delegates to instead of duplicating that
  logic locally.
- **`products` table** (20 seeded rows) — name, brand, category, skin
  types/concerns, key ingredients, price, usage instructions, sensitivity
  warnings. `backend/src/services/productRecommendation.js` filters and
  scores the catalog against a user's skin type/concerns/allergies (never
  recommending a product that conflicts with a declared allergy) and is
  called automatically every time a skincare plan is generated.
- **`product_recommendations` table** — an audit row per product
  recommended alongside a specific plan generation, so recommendations
  persist across reloads (`GET /api/products/recommendations`) and Admin
  analytics can report on recommendation volume over time.

On the User dashboard, this surfaces as a dedicated **"Ingredients &
Products"** tab (personalized "For You" view + a searchable "Browse All
Ingredients" catalog), plus compact "Product Recommendations" and
"Suitable Ingredients" sections embedded directly in the Skincare Plan
tab.

## 11. Docker deployment

The whole stack (Postgres, the Flask ML service, the Express API, and the
React SPA behind nginx) can run with Docker Compose — no local Node,
Python, or Postgres install required.

**Files:** `backend/Dockerfile` (+`docker-entrypoint.sh`), `ml/Dockerfile`,
`frontend/Dockerfile` (+`nginx.conf`), and the root `docker-compose.yml`.

```bash
# 1. From the project root, create your env file
cp .env.example .env
# then edit .env — at minimum set JWT_SECRET, SESSION_SECRET, and a real
# PGPASSWORD. Google OAuth vars can stay blank (Google login just won't
# be offered).

# 2. Build and start everything
docker compose up --build

# 3. Open the app
#    Frontend:     http://localhost:5173
#    Backend API:  http://localhost:5000/api/health
#    ML service:   http://localhost:5001/health
```

What happens on `up --build`:
- **postgres** starts with a named volume (`pgdata`) so data survives
  restarts, and exposes a healthcheck the other services wait on.
- **ml-service** builds the demo scikit-learn pipeline into a Flask app
  served by gunicorn.
- **backend**'s entrypoint waits for Postgres to accept connections, then
  runs `src/db/init.js` — this is safe to run on every container start,
  since `schema.sql` uses `CREATE TABLE/TYPE IF NOT EXISTS` and the demo
  account seed uses `ON CONFLICT DO NOTHING`, so it never touches existing
  data — then starts the API. Uploaded photos persist in the `uploads`
  named volume.
- **frontend** is built as a static Vite bundle and served by nginx, with
  a fallback route so React Router's client-side routes work on refresh.
  `VITE_API_URL`/`VITE_SERVER_URL` are baked in at build time (Vite
  inlines `import.meta.env.*` at build, not runtime) — if you deploy the
  frontend at a different host/port than the defaults, set those two
  build args in `.env` before running `docker compose up --build`.

To stop everything: `docker compose down` (add `-v` to also delete the
Postgres/uploads volumes and start completely fresh next time).

Local (non-Docker) development, as described in sections 3–5 above, is
untouched by any of this — the Dockerfiles are additive.
